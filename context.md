## 🏛️ 3. Модуль «Опись основных средств (ОС и НМА)»

Модуль предназначен для физической и финансовой инвентаризации оборудования, кухонной техники, мебели и IT-устройств ресторана.

### Архитектура модуля:
* **База данных (`Supabase`):** таблица **`assets`** (не `fixed_assets` — такой таблицы в БД нет).
  * Реальные поля: `id` (uuid), `inv_number`, `name`, `category`, `location`, `responsible_person` (МОЛ), `quantity`, `initial_cost`, `commissioning_date`, `status` (`in_use`, `in_stock`, `repair`, `written_off`, `archived`), `serial_number`, `notes`, `photo_url`, `last_inventoried_at`, `created_at`, `updated_at`, `location_id`, `source`.
  * ⚠️ Полей амортизации (`salvage_value`, `useful_life_months`, `accumulated_depreciation`, `book_value`, `depreciation_method`) и `iiko_id` в таблице **нет**. Попытка записать несуществующую колонку даёт `400 PGRST204`.
* **API Эндпоинты** (все — `admin` + `manager`):
  * `/api/iiko/assets` (GET, POST, PUT, DELETE) — CRUD. `PUT` с `action: "audit"` проставляет `last_inventoried_at`.
  * `/api/iiko/assets/sync` (POST) — сверка со справочником «Оборудование» iiko, см. **3.10**.
  * `/api/iiko/assets/split` (POST) — разворот партии в поштучные карточки.
  * `/api/iiko/assets/locations`, `/api/iiko/assets/tags` — места и наклейки, см. **3.11**.
* **Публичные страницы** (`app/asset/[id]`, `app/tag/[code]`) — **данных не показывают**, только код наклейки. Их открывает любой, кто навёл камеру; подробности см. 3.11.
* **UI Компонент:** `FixedAssetsView` внутри `components/LocmacoApp.jsx`
  * KPI: первоначальная стоимость, в эксплуатации, на обслуживании.
  * **Наклейки** — универсальные, печатаются пачкой пустыми (3.11). Печать стикера под конкретную позицию убрана.
  * **Инвентаризация сканером** (`InventoryScanModal`): живой счётчик «отсканировано X из Y», список пропущенных, запись `last_inventoried_at` по завершении. Работает в любом браузере с камерой (3.9).
  * **Экспорт CSV** — выгрузка текущей выборки (UTF-8 BOM, открывается в Excel с кириллицей).
  * Категорий у оборудования нет — поле убрано за ненадобностью.
  * На телефоне вместо таблицы — карточки (3.11).

## 📊 3.1. Модуль «Отчеты» — месячная сводка кассы (только `admin`)

Повторяет бумажную таблицу бухгалтерии: по дням месяца — типы оплат от кассира слева, продажи iiko справа, расхождение.

* **API:** `/api/iiko/reports/monthly-cash?month=YYYY-MM` (GET, только `admin`).
  * Один OLAP-запрос в iiko (`SALES`, группировка по `OpenDate.Typed`) + одна выборка `bot_actions` (`action_type=cash`), агрегация по дням.
* **UI:** `MonthlyReportsView`. Селектор месяца, подсветка выходных, строка ИТОГО, экспорт CSV.

### ⚠️ Формула колонок — выверена на живых данных, не менять наугад
| Колонка | Источник |
| :--- | :--- |
| **Наличные -** | `payments.cash + payments.encashment + details.total_expenses` |
| **Наличные фискал** | `payments.cash` |
| HUMO / Uzcard / Рахмат / Uzum / Yandex | соответствующие поля `payments` |
| **Общая Сумма** | «Наличные -» + все безналичные типы + `online` |
| **iiko сумма продаж** | `DishDiscountSumInt` из OLAP за день |
| **Разница** | Общая Сумма − iiko |

**Цвета колонки «Разница»:** красный — недостача (сдали меньше, чем продали), зелёный — излишек, серый — сошлось. Знак: `diff < 0` это недостача.

**Почему так:** `cash` (фискал) и `encashment` — два независимых поля формы кассира, оба входят в выручку смены. Расходы кассира (`total_expenses`) — это тоже наличные от продаж, просто вышедшие из ящика до сдачи. Без них отчёт занижен ровно на сумму расходов. После включения всех трёх слагаемых расхождение с iiko за июнь 2026 упало до **+10 288 сум на 584 млн** (0.002%) — это округление копеек, а не ошибка.

## 🗂 3.2. Правка сданной кассовой смены (только `admin`)

Смены раньше были write-once: ошибка кассира (не заполнил фискальные наличные, поставил не ту дату) навсегда искажала отчёт.

* **API:** `/api/iiko/cash`
  * `GET ?from&to` — список сданных смен за период.
  * `PATCH` — правка по `id`. Частичная: не переданное поле сохраняет прежнее значение.
* **Производные пересчитываются на сервере** (`total_sales`, `total_expenses`, `difference`, `iiko_cash`) по той же формуле, что при сдаче — от клиента не принимаются.
* **Аудит обязателен:** каждая правка пишет в `details.edit_history` запись `{edited_at, edited_by, reason, changes: {поле: {from, to}}}` и отдельное действие `cash_edit` в `bot_actions`. Причина правки обязательна в UI.
* **UI:** блок «Сданные смены — правка» внизу вкладки «Касса». Смены с `cash = 0` при ненулевой `encashment` подсвечены красным — это типовой косяк кассира.
* Правка **сразу меняет цифры** в «Отчетах» и аналитике — они читают те же записи.
* Таблица `cash_reports` заполняется при сдаче, но **не читается нигде** (мёртвый код); правки её намеренно не трогают.

## 🤖 3.3. Модуль «Агент» — ИИ-аналитик iiko (только `admin`)

Чат на сайте: вопрос на русском → агент сам тянет данные из iiko и отвечает. **Строго read-only**, записи в iiko нет.

* **Модель:** `claude-opus-5` через `@anthropic-ai/sdk`. Требуется `ANTHROPIC_API_KEY` в окружении.
* **API:** `/api/iiko/agent/chat` (POST, SSE-стриминг, только `admin`). Лежит под `/api/iiko/`, чтобы существующий `middleware.js` проверял сессию.
* **Файлы:**
  * `lib/agent/skills.js` — 7 методик расчёта, портированных 1:1 из Python-скриптов владельца (`~/Documents/ai_/lokma_agent/queries/*.py`). Порт сверен с iiko: `daily_revenue` за июнь 2026 даёт `584 111 130` — совпадает с отчётом по кассе.
  * `lib/agent/tools.js` — определения инструментов + `raw_olap` для нестандартных разрезов.
  * `lib/agent/prompt.js` — системный промпт (адаптирован из `AGENT_PROMPT.md` владельца).

### Ключевые особенности данных iiko — учтены в промпте и скиллах
1. **`GuestNum` недостоверен** — 95.5% чеков с `GuestNum=1` (дефолт кассы). «Гости» = количество **столов/чеков**, не людей.
2. **`OrderNum` не уникален глобально** — сбрасывается ежедневно. Чек = пара (дата, `OrderNum`).
3. **`DishCategory` пустая** — для группировки блюд использовать `DishGroup`.
4. **`OrderType` пустой** — вся выручка идёт как зал.
5. **Дата-поле для `TRANSACTIONS` — `DateTime.Typed`** (не `OpenDate.Typed`). Другие названия дают `Unknown OLAP field`.
6. **Верхняя граница периода не включается** (`includeHigh=false`): весь июнь = `from=2026-06-01&to=2026-07-01`.
7. **Агрегация `TRANSACTIONS` бывает неточной.** Прецедент: счёт «Налог» агрегацией дал 45 995 700, пересчётом по документам — 70 246 235. Перед финальной цифрой по статье расходов агент обязан вызвать `verify_expense_account`.

### Маппинг мест приготовления (`CookingPlace`)
`1.1 Кухня`, `1.6 Кухня + Фрукты`, `1.4 Фрук`, `1.7 Горячий цех`, `1.8 Холодный цех`, `1.9 Пицца` → **Кухня**; `1.2 Бар` → **Бар**; `1.3 Мороженое` → **Мороженое**. Цеха появились 03.07.2026 — за более ранние периоды их нет. Список не статичен и пополняется.

## 📦 3.4. Раздел «Инвентаризация» — расхождения (только `admin`)

Раздел показывает **отчёт о расхождениях** по проведённым пересчётам. Форма проведения инвентаризации из UI убрана: компонент `InventoryView` остался в коде, но нигде не рендерится, и `POST /api/iiko/inventory` больше не вызывается с сайта. Пересчёты проводятся в iiko-офисе.

* **API:** `/api/iiko/reports/inventories?from&to` (GET, только `admin`).
* **UI:** `InventoriesReport` — таблица: дата, документ, склад, излишки (сумма и %), недостача (сумма и %).

### ⚠️ Как считать расхождения — иначе получишь ноль
Проводки инвентаризации идут **двойной записью**, поэтому сумма по документу всегда равна нулю. Реальные величины лежат на счетах `Излишки инвентаризации` и `Недостача инвентаризации`; фильтр — `TransactionType = INVENTORY_CORRECTION`. Документы инвентаризации через `documents/export/inventory` и подобные пути **не отдаются** (404) — только через OLAP TRANSACTIONS.

### База процента — выручка своего направления
| Склад | Места приготовления в базе |
| :--- | :--- |
| Кухня главная | `1.1 Кухня`, `1.3 Мороженое`, `1.4 Фрук`, `1.6 Кухня + Фрукты` |
| Кухня подвал | `1.7 Горячий цех`, `1.8 Холодный цех`, `1.9 Пицца` |
| Бар | `1.2 Бар` |
| Основной склад, Заготовочный цех | вся выручка заведения |

Считать от общего COGS **нельзя** — это занижает картину по мелким складам вдвое и больше.

**Находка на 31.07.2026:** Кухня подвал — недостача 25 931 685 при выручке подвала 91 246 310 за июль, то есть **28.4%**, при излишках всего 3.8%. Остальные склады укладываются в ±4%. Подвал заработал только в июле, так что это, вероятно, накопленное с запуска (непроведённые заготовки и перемещения), но требует разбора по 288 позициям документа.

## 💰 3.6. Сейф — административные расходы (`admin_expense`)

Раздел «💰 Сейф» внутри Аналитики. Расходы, оплаченные не из кассы, а из сейфа: зарплаты, аренда, крупные закупки.

* **Хранение:** `bot_actions` с `action_type = "admin_expense"`, `details: {name, amount, selected_date}`.
* **API:** `/api/iiko/analytics/cash-expenses` — GET (список + баланс), POST (создать), DELETE (удалить). Только `admin`.
* ⚠️ **`tg_id` в таблице — bigint.** Передача строки (`"admin"`) даёт `400 22P02 invalid input syntax for type bigint`. Использовать числовой id.

### Формула остатка
```
Остаток в сейфе = Σ payments.cash по всем сменам − Σ admin_expense
```
Берётся именно `payments.cash` (фискальные наличные), без `encashment` и без расходов кассира.

### Незакрытый вопрос: расхождение 319 520
02.08.2026 общая строка «расходы» на 402 155 480 от 12.06 была заменена детализацией из 12 записей на 402 475 000 (Ташкент продукты, зарплаты, аренда, блогеры, кафель). Разница **319 520**: со старой суммой остаток на 12.06 давал ровно фактические 129 035 000, с новой — 128 715 480.

Источник разницы не найден: смены с недостачей ровно 319 520 нет (ближайшая 23.04, −372 444). Временная правка +319 520 к `payments.cash` смены 01.06 вносилась и **была откатана по просьбе владельца** — сейчас расхождение снова открыто. Вероятно, одна из 12 сумм округлена до ровного числа.

## 📈 3.7. Выручка по категориям — не склеивать группы

В «Аналитике» блок «Выручка по категориям» строится по `DishGroup.TopParent` (группы меню), **не по `CookingPlace`**.

Раньше всё, кроме «Бара», сваливалось в выдуманную группу «Кухня», а настоящие категории iiko становились её подгруппами — из-за этого два разных производства читались одним числом. Сейчас группы берутся как есть из iiko.

Эмодзи подбирается по названию, новые категории подхватываются автоматически.

## 📷 3.8. Фотофиксация прихода (товар + накладная)

Порядок шагов: **Поставщик → Склад → Накладная → Товары**.

Фотография накладной **обязательна**: без неё кнопка «Далее — товары» заблокирована, и то же самое проверяет сервер (`400`, если среди вложений нет `kind: "invoice"`) — чтобы требование нельзя было обойти мимо интерфейса. Фото каждой позиции при этом остаётся **необязательным**: часть товаров снабженец может оставить без снимка.

> ⚠️ Требование включается, только если `storageConfigured()` — то есть задан `SUPABASE_SERVICE_KEY`. Иначе ненастроенное хранилище остановило бы приёмку товара целиком: фото физически загрузить нельзя, а приход провести надо. В этом случае интерфейс показывает предупреждение и пропускает дальше.

При создании прихода кладовщик прикладывает фотографии: **к каждой позиции** — что реально привезли, и **отдельно к документу** — накладную поставщика. Снимать можно камерой (`capture="environment"`) или выбрать из галереи; принимаются jpeg/png/webp/heic и PDF.

**В iiko фотографии не уходят** — там остаётся обычная приходная накладная. Фото живут только на сайте.

### Где что лежит
| Что | Где |
| :--- | :--- |
| Файлы | Supabase Storage, приватный бакет `invoice-photos`, путь `<draft_id>/<kind>-<ts>-<rnd>.<ext>` |
| Метаданные | `bot_actions.details.photos[]` записи `action_type = "invoice"` |
| Флаги полноты | `details.has_invoice_photo`, `details.items_without_photo[]`, `details.photos_complete` |

Флаги считаются **на сервере в момент проведения** (`buildPhotoDetails` в `app/api/iiko/invoice/route.js`) и хранятся в базе, а не выводятся на лету: если состав позиций потом изменится, отметка «фото не было» должна остаться такой, какой была при приёмке.

### Ключи и доступ
* Бакет **приватный**. Прямая ссылка из браузера ничего не отдаст — картинка идёт через `GET /api/iiko/invoice/photos?path=…` с проверкой роли.
* Для загрузки и чтения нужен **`SUPABASE_SERVICE_KEY`** (service_role) в `.env` и в проде. Анонимный ключ не может ни создать бакет, ни писать в приватный объект. Без переменной загрузка отвечает `503` с понятным текстом, остальной приход работает как раньше.
* Бакет создаётся автоматически при первой загрузке (`ensureInvoiceBucket` в `lib/storage.js`).
* Роли: загружать — `admin`, `supplier` (те же, кто может делать приход); **смотреть — только `admin`**.

> ⚠️ Легаси-расхождение ролей. В `hasAccess` вкладка «Приход» открыта только `supplier` (+ `admin`), а в API `/api/iiko/invoice` исторически стоял список `["admin", "director", "supplier"]` — кнопки у директора нет, но эндпоинт его пускал. Исправлено 09.08.2026. **Такой же разъезд остался в `/api/iiko/transfer`** (`allowedRoles` включает `director`, а вкладки «Перемещение» у него нет) — не трогали, проверить отдельно.

### Фото необязательны, но отсутствие видно
Приход проводится и без единого снимка. Но:
* в форме под позицией без фото стоит «фото не прикреплено», а перед кнопкой «Провести» — жёлтый блок со списком того, чего не хватает;
* в истории карточка получает бейдж `📷 Фото: N` (зелёный) либо `⚠️ Фото приложены не полностью` (жёлтый);
* админ жмёт «📂 Открыть накладную» и видит модалку: позиции, суммы, миниатюры по каждому товару, фото накладной и явные пометки `📵 фотография не прикреплена`.

Снимки сжимаются в браузере до 1600px / JPEG q0.82 перед отправкой — иначе 4-мегабайтные фото с телефона на мобильном интернете грузятся минутами.

### Фотоотчёт в Telegram-группу
После успешного проведения бот кидает в `TG_INVOICE_CHAT_ID` (если не задан — в общий `TG_CHAT_ID`) альбом: **сверху снимок накладной, снизу коллаж позиций**, подпись — номер, поставщик, склад, список позиций с суммами, итог и пометка о недостающих фото (`lib/telegram.js`).

Коллаж клеится **в браузере** через canvas (`buildCollage`) и грузится в бакет как `kind: "collage"`: на сервере нет ни `sharp`, ни `canvas`, а тянуть нативный модуль ради склейки не стали. По одному снимку на позицию, не больше 9 на картинку — дальше ячейки нечитаемы; позиций больше — несколько коллажей (Telegram берёт до 10 медиа в альбоме).

Если фото нет вовсе — уходит обычное текстовое сообщение. Ошибки Telegram только логируются: приход к этому моменту уже проведён в iiko, ронять его из-за недоступного бота нельзя. Коллаж не считается в бейдже «📷 Фото: N» — это служебная картинка, а не документ приёмки.

## 📱 3.9. Сканер QR — почему не хватает BarcodeDetector

`BarcodeDetector` реализован **только в Chromium**. В WebKit его нет ни в одной версии Safari, а на iPhone все браузеры (включая Chrome и Яндекс) — это WebKit. Раньше сканер ОС на айфоне выдавал «нужен Safari 17+» и не работал вообще: формулировка была неверной, никакая версия Safari не помогла бы.

Сейчас два пути: если `BarcodeDetector` есть — используем его (аппаратный, быстрый), иначе динамически подгружается **`jsqr`** и кадры декодируются на canvas. Работает на любом браузере с камерой.

Программное декодирование ограничено 10 кадрами в секунду и кадром 640px по ширине — полный кадр jsQR жуёт слишком долго и греет телефон.

> ⚠️ Камера требует **https**: `getUserMedia` в незащищённом контексте недоступна. Если открыть сайт по http, сканер сообщит об этом явно.

## 🔄 3.10. Синхронизация ОС с iiko — зеркало справочника

Справочник «Оборудование» в iiko — **источник истины**. Сверка (`/api/iiko/assets/sync`) приводит базу сайта к нему:

| В iiko | На сайте |
| :--- | :--- |
| появилась номенклатура | создаётся карточка (партия >1 шт — сразу поштучные карточки со своими QR) |
| переименована | имя обновляется |
| убрана из группы / удалена | карточка получает `status = "archived"`, **не удаляется** |
| вернулась обратно | статус снова `in_use` |

> ⚠️ `archived` — это **не списание ОС**. Никаких проводок, ни в iiko, ни в учёте ничего не меняется: карточка просто уходит из рабочего списка, потому что в справочнике iiko её больше нет. Настоящее списание — отдельный статус `written_off`, его ставит бухгалтерия руками, и **сверка такие карточки не трогает вовсе**. Смешивать эти два состояния нельзя: через полгода не разобрать, что оборудование выбыло, а что просто вычистили из справочника.

Архив не удаляем: за карточкой могут стоять напечатанные наклейки и отметки инвентаризации. В списке он скрыт — фильтр «⚡ Действующие» (по умолчанию) прячет `archived`, посмотреть можно через «📦 Нет в iiko (архив)» или «🗂 Все, включая архив».

**Цену и дату ввода сверка не затирает** — их правят руками на сайте, обновляются только если пустые.

### Автозапуск
Сверка стартует сама при открытии раздела ОС, тихо, в фоне. Тост показывается только если что-то реально изменилось. Сервер пропускает автозапуск, если прошлая сверка была меньше **30 минут** назад (`AUTO_SYNC_INTERVAL_MS`): полный проход тянет из iiko накладные за два года, гонять его на каждое открытие страницы незачем. Кнопка «⚡ Импортировать приходы из iiko» запускает сверку принудительно, без этого ограничения.

### ⚠️ Баг базового номера — почему сверка раньше ничего не находила
Партия разворачивается в `EQ-00690-01 … EQ-00690-20`, и по базе `EQ-00690` карточки собираются обратно в одну строку. Базовый номер вычислялся как `replace(/-\d+$/, "")` — и у обычной позиции `EQ-00690` съедал номер целиком, оставляя `EQ`.

Последствия: все позиции схлопывались в одну «партию» по имени, а сверка считала, что в базе нет ни одной позиции из iiko. Теперь есть `lib/inv-number.js` — суффикс экземпляра определяется по количеству сегментов (третий сегмент), а не регуляркой. Используется в sync, split и группировке списка.

## 🏷 3.11. Места и универсальные QR-наклейки (только на сайте)

Ни мест, ни наклеек в iiko нет — это учёт исключительно сайта. Миграция: `supabase/migrations/20260810_asset_locations_and_tags.sql`.

### Места
Плоский список (`asset_locations`), у карточки — `assets.location_id`. Старое текстовое `assets.location` **не трогаем**: в него пишет легаси-бот. До этого поле было фикцией — у всех 169 карточек стояло одно и то же «Кухня / Ресторан».

Место с оборудованием удалить нельзя: сначала перенести карточки.

### Универсальный QR — почему так, а не стикер под позицию
Раньше: сгенерил QR под конкретную позицию → напечатал → **пошёл искать, к чему приклеить**. Здесь и рождается путаница: наклейку от одной морозилки легко налепить на другую, и потом это уже не выловить.

Сейчас порядок обратный:
1. Печатается пачка **пустых** наклеек `LKM-0001…` (сетка 4 колонки на A4, QR ведёт на `/tag/LKM-0007`).
2. Клеятся на что угодно — в этот момент неважно, на что именно.
3. Подошёл, отсканировал, выбрал из списка что это и где стоит — привязка сохраняется.

Ошибиться почти невозможно: выбор делается, когда предмет перед глазами.

**Инварианты:**
* `asset_tags_asset_uniq` — одна единица не может иметь две наклейки. Свободных наклеек при этом сколько угодно.
* Перепривязка занятой наклейки требует `force` и подтверждения: случайный скан не должен молча переклеить учёт.
* Нумерация продолжается от последнего кода — новая пачка не пересекается со старой.

### Оборудование, заведённое на сайте (`assets.source`)
Карточку можно создать руками — в том числе прямо на экране привязки наклейки, если нужного оборудования нет в списке.

`source = 'manual'` для таких карточек, `'iiko'` (по умолчанию) для импортных. **Сверка архивирует только `source = 'iiko'`**: заведённого руками в справочнике iiko нет по определению, и без этого признака оно уезжало бы в архив на первой же сверке.

> ⚠️ **Дубли.** Если создать позицию на сайте, а потом завести её же в iiko — получатся две карточки: ручная (`INV-…`) и импортная (`EQ-…`). Автоматически они не склеиваются: сопоставление идёт по инвентарному номеру, а он у них разный.
>
> Как чинить: открыть ручную карточку и поставить ей `inv_number` из iiko (`EQ-00712`) **до** ближайшей сверки — тогда сверка узнает её как свою и просто обновит. Если дубль уже создался, лишнюю карточку удалить, предварительно переклеив наклейку на оставшуюся.
>
> Как не попадать: заводить новое оборудование либо только в iiko (и дождаться сверки), либо только на сайте.

### Мобильная версия раздела
Раздел ОС правят и сканируют с телефона, поэтому там отдельная вёрстка:
* вместо таблицы на семь колонок — **карточки** (`useIsMobile`, порог 767px — тот же, что у медиазапросов в `globals.css`);
* кнопки шапки разворачиваются в колонку во всю ширину (`.stack-mobile`);
* тач-таргеты не меньше 44px (`.touch-btn`);
* модалки мест, наклеек и привязки открываются на весь экран (`.sheet-mobile`);
* поля ввода принудительно 16px — иначе iOS зумит страницу при фокусе.

Категорий у оборудования больше нет: фильтр, поле в форме, колонка в CSV и строка в QR убраны — на практике все позиции были «Оборудование».

### Что видно при сканировании
| Кто сканирует | Что происходит |
| :--- | :--- |
| Обычная камера телефона | `/tag/<code>` — **только код и подпись «Инвентарная наклейка оборудования»**. Никаких данных |
| Сайт → «🔍 Найти по QR» | Полная карточка: название, место, стоимость, МОЛ, дата инвентаризации, кнопка «Изменить» |
| Сканер инвентаризации | Засчитывает единицу; понимает и коды наклеек, и старые стикеры с инв. номером |
| Экран привязки | Показывает код и предлагает выбрать оборудование и место |

> ⚠️ **Публичные страницы данных не показывают — намеренно.** Наклейки висят в зале и на кухне, их сканируют гости и линейный персонал. Стоимость оборудования — не та информация, которую стоит показывать всем подряд. По этой же причине выпотрошена и старая `/asset/[id]`.
>
> Старые стикеры, где данные зашиты **текстом внутрь самого QR**, так не закрыть: там информация не на странице, а в самом коде. Такие наклейки нужно перепечатать универсальными.

### Партии: одна номенклатура iiko — N карточек на сайте
Пришло 20 столов — в iiko это **одна** номенклатура на 20 штук, а на сайте должно стать **20 карточек** `EQ-00745-01 … EQ-00745-20`, у каждой своя наклейка. Так требует учёт ОС: у каждой единицы свой инвентарный номер, своя судьба (ремонт, списание, перемещение).

Разворот срабатывает при **первом** создании карточки. Позиции, попавшие в базу раньше этой логики, лежат одной строкой с `quantity > 1` — для них кнопка **«✂️ Развернуть партии (N)»** в шапке раздела: показывает список и суммарное число карточек, разворачивает всё разом. Операция необратимая, схлопнуть обратно нельзя.

> ⚠️ Разбивка **переиспользует исходную карточку** как первый экземпляр, а не удаляет её. Иначе вместе с удалённой карточкой отвязывалась бы наклейка и терялись отметки инвентаризации.

При скане показывается номер экземпляра — «Стол · №3 из 7» (`unitLabel`), иначе непонятно, какой именно из двадцати одинаковых предметов перед тобой.

### Что считается ОС, а что расходкой
Поштучные карточки и наклейки нужны там, где важна **конкретная единица**: стол, стул, холодильник, кофемолка, рация. У каждой своя судьба — ремонт, перемещение, списание, и по учёту у каждой свой инвентарный номер. Двадцать одинаковых столов — это двадцать карточек и двадцать наклеек, а не одна позиция с количеством.

Расходка (салфетницы, кубы, чехлы) в справочнике ОС не нужна вовсе: заводить на неё карточки и клеить наклейки бессмысленно. Такие позиции **убираются из группы «Оборудование» в iiko** — 10.08.2026 так поступили с «Салфетница», «Куб», «Чехол для столов».

### Что происходит, когда позицию убирают из группы iiko
1. Ближайшая сверка переводит её карточки в `archived` («📦 Нет в iiko»), из рабочего списка они пропадают.
2. Карточки **не удаляются**: вернут позицию в справочник — оживут сами.
3. Кнопка «✂️ Развернуть партии» пересчитывается: убранное из неё исчезает.
4. Наклейки, привязанные к архивным карточкам, **остаются занятыми**. Чтобы пустить их в дело — отвязать через «🏷 Наклейки» → «Привязанные».

Сверка идёт автоматически при открытии раздела, но не чаще раза в 30 минут; кнопка «⚡ Импортировать приходы из iiko» запускает немедленно.

### ⚠️ Печать: без всплывающего окна
Лист наклеек рендерится **в саму страницу** и печатается через `@media print` (класс `printing-tags` на `body`, контейнер `#print-tags` в `globals.css`).

Через `window.open` не получится: окно открывается после `await` — создание пачки идёт запросом, — и браузер такое окно не считает результатом клика. Возвращается `null`, обращение к `null.document` падает с «Cannot read properties of null». Именно поэтому пачка создавалась, а лист печати не открывался.

QR тянутся с внешнего `api.qrserver.com`, поэтому перед печатью ждём загрузки картинок — иначе на лист уходят пустые рамки.

### Привязка с карточки
Кнопка «📱 QR-код» в списке заменена на **«🏷 Привязать / Переклеить»**: нажимаешь на нужной позиции, сканируешь свободную наклейку — связались. Печать стикера под конкретную позицию убрана, наклейки печатаются только пачками.

### Свободные наклейки
Созданная пачка не теряется, если закрыть страницу: коды уже в базе. В окне наклеек — «🖨 Печатать свободные (N)» для повторной печати всех непривязанных и корзина, чтобы удалить лишние (привязанную удалить нельзя, сначала отвязать).

## 🧾 4. Бухгалтерский и налоговый контекст (1С и iiko)

### 4.1. Специфика закупа (Безнал vs Базар):
1. **Официальный закуп (Безнал / КПК / Расчетный счет):**
   * Поставщики с формами MCHJ, ООО, XK, AJ (например, *FAR TRADE EXPERT MCHJ*).
   * Имеется официальный счет-фактура / КП. Дает 100% зачет НДС и принимается в 1С.
   * Примеры товаров: Мука (*Мука*, *Мука Mama Mia* — 100% безнал), упаковка, фирменные соусы, напитки.
2. **Наличный закуп (Базар / Снабженец):**
   * Закупки производит снабженец на базаре за наличные.
   * Первичных официальных документов нет.
   * Примеры товаров: Свежие ягоды (клубника, банан), зелень, свежие овощи (доля безнала ~1%).

### 4.2. Правило списания для 1С (Коэффициент списания):
* ❌ **НЕЛЬЗЯ использовать единый плоский процент (например, 35-40% на всё):**
  * По товарам со 100% безналом (мука) возникнет гигантский виртуальный пересорт в 1С (приход 100%, списание 35%).
  * По товарам с базара (бананы) 1С уйдет в **красные минусовые остатки на счетах ТМЦ (2910/1010)**, так как безналичного прихода не было.
* ✅ **ПРАВИЛЬНЫЙ ПОДХОД:** Применять дифференцированные коэффициенты по группам номенклатур (на основе скрипта `calculate_all_ingredients_ratio.mjs`):
  * Группа 100% безнал (мука, упаковка): Списание 100% от расхода iiko (коэфф `1.0`).
  * Группа смешанного закупа (мясо, молочка): Списание по расчитанному коэффициенту (напр. `0.65`–`0.75`).
  * Группа чисто наличного закупа (базар): Списание только в пределах имеющихся безналичных накладных / авансовых отчетов.

* **Авторизация iiko Server:** `GET /resto/api/auth?login=...&pass=sha1(пароль)`, далее `Cookie: key=<token>`. Обязателен заголовок `User-Agent` — без него сервер отдаёт 500.
* **Особенность XML формата `incomingInvoice`:**
  * Запрос `/resto/api/documents/export/incomingInvoice` с заголовком `Accept: application/json` возвращает массив пустых объектов `[{}, {}]`.
  * **ОБЯЗАТЕЛЬНО** передавать `Accept: application/xml` и парсить ответ с помощью XML-парсера или регулярных выражений.

## 🧪 6. Текущий статус и сборка

1. **Зависимости:** установлены. Добавлены `@anthropic-ai/sdk` (модуль «Агент») и `jsqr` (сканер в WebKit).
2. **Сборка:** `npm run build` проходит без ошибок.
3. **Переменные окружения на проде:**
   * `ANTHROPIC_API_KEY` — без него вкладка «Агент» отвечает ошибкой, остальное работает.
   * `SUPABASE_SERVICE_KEY` (service_role) — фотографии приходов. Без него загрузка отвечает `503`, а требование фото накладной автоматически отключается, чтобы не встала приёмка товара.
   * `TG_INVOICE_CHAT_ID` — куда шлётся фотоотчёт о приходе. Запасного варианта нет намеренно: прежний `TG_CHAT_ID` — мёртвое наследство старого бота, бот в том чате не состоит.
4. **Миграции выполняются руками** в Supabase → SQL Editor: анонимный ключ не имеет прав на DDL. Файлы в `supabase/migrations/`.
5. **Не проверено вживую:** поведение агента (выбор инструментов, формулировки) — скиллы сверены с iiko, но сам диалог не обкатан.

> ⚠️ У сайта и Telegram-бота отчётов **разные боты**. Токен на проде — не тот, что в `bot_lokmaco/.env`. Бот, которым пользуется сайт, должен быть добавлен в целевой чат администратором с правом публикации, иначе Telegram отвечает `chat not found` — тем же текстом, что и при несуществующем чате.
